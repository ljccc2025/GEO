## 一、项目背景与目标

### 1.1 业务背景

公司是**工业设计出口企业**，当前品类**耳塞**（后续可能扩展），目标客户是**海外买手**。公司目前**没有域名、没有官网**。

### 1.2 要解决的问题

海外买家的采购习惯正从「搜索引擎 → 逐个点开网页」转向「直接问 AI」。当买手问 AI「推荐中国优秀的耳塞设计工厂」时，答案里没有本公司——因为 AI 不知道我们存在。

### 1.3 目标

**让 AI 在回答设计/供应商相关问题时，答案中包含并推荐本公司。**

### 1.4 打法（已与需求方确认）

**真实内容 × 广泛分发。不做内容农场。**

AI 引擎和搜索引擎都在识别低质 AI 生成内容，编造内容批量投放会被过滤，严重时域名被打标记。系统的**内容质量门禁**是这套打法能否长期有效的关键。

### 4.3 ⚠️ 三个被审查抓到的问题（请务必阅读）

这三个问题**如果没被两阶段审查抓到，后面会非常难查**。把它们的成因记住，能帮你避免同类错误：

#### 问题 1：把 fail-closed 改成了 fail-open

首次实现往 `AiProviderEndpointPolicy::MODEL_HOSTS` 加了 `'openai' => ['openai.com']`。

- 改动前：未知 `binding_type` → `MODEL_HOSTS[x] ?? []` 为空数组 → 返回 false → **拒绝**
- 改动后：同样的调用**会通过校验**
- 而下游 `AdminAiSourceProviderService::modelSettingKey()` 对非 `ark` 一律回退到 **DeepSeek 的 setting key**
- 后果：一旦有调用方绕过 FormRequest 传入 `binding_type='openai'`，会带着 OpenAI 的 api_url **去改写 DeepSeek 的模型绑定**——一次静默的绑定错乱

**修法**：直接**删除该键**（本计划两个海外引擎都是检索型，走 `acceptsSearchApi()`，根本不需要它）。

> **教训**：往安全相关的白名单/映射表里「预留」条目，可能改变未知输入的处理语义。**未知输入应当 fail closed。**

#### 问题 2：后缀匹配语义下白名单过宽

写 `'openai.com'` / `'perplexity.ai'` 时，由于匹配逻辑是
`$host === $trustedHost || str_ends_with($host, '.'.$trustedHost)`，
等于放行该顶级域下的**全部子域**。实际只需要 `api.openai.com` 与 `api.perplexity.ai`。

**修法**：收紧为 `api.openai.com` / `api.perplexity.ai`，并补一个 `evil.perplexity.ai` 必须被拒的用例来证明收紧生效。

#### 问题 3：★ 计划本身写错了 —— 引擎清单并非单一来源

**实现计划里我写了「8 个分析类文件引用 `SAMPLE_PROVIDERS` 常量，新引擎挂上后自动生效，一行都不用改」。这句话是错的。**

审查者证明有**两处硬编码**了引擎列表：

```php
// app/Http/Controllers/Admin/AiVisibilityAnalyticsController.php:47-51
'providers' => [PROVIDER_DOUBAO_ARK_RESPONSES, PROVIDER_DOUBAO_SEARCH_CUSTOM, PROVIDER_DEEPSEEK_ANALYSIS],

// app/Services/Admin/Analytics/AiVisibilityAnalyticsFilter.php:21-26
if (! in_array($provider, ['all', ...同样三个硬编码...], true)) { $provider = 'all'; }
```

**后果**：KPI 统计里**包含**新引擎，但下拉框里**看不到**、按新引擎筛选会被**静默重置为 all**——改之前三处是对齐的，这个改动**引入了不一致**。

**修法**：两处都改为引用 `AiVisibilityRun::SAMPLE_PROVIDERS`，并给 4 个语言文件补上新引擎显示名（`lang/{en,zh_CN,zh_TW,pt_BR}/admin.php`）。

> **教训**：**不要相信「单一来源」的说法，要用 grep 验证。** 遇到「挂个常量就自动生效」这类判断，必须实际搜索硬编码。

## 五、关键设计决策与原因

| 决策 | 结论 | 原因 |
|---|---|---|
| 交付物形态 | **内部 GEO 作战平台**（Web 应用），**不是**给买手看的官网 | 需求方明确：「就是一个类似包含这个功能的网页」 |
| 租户模型 | **对内单租户** | 只服务本公司获客，不对外提供 GEO 服务 |
| 底座选型 | **GEOFlow**（PHP 8.3 / Laravel / AGPL-3.0） | 唯一自带完整内容生产闭环 + 企业级治理 + 配置驱动的项目 |
| 许可证边界 | 内网使用；**对公众只发静态产物** | AGPL 第 13 条；用 `front_mode=static` 输出静态 HTML 可完全规避 |
| 被否方案 | GEORank + 自研 / 纯自研 / GEOFlow+独立官网 | 见规格 §4.2 |
| 业务信息 | 品类、能力点、目标问题**全部配置化** | 需求方尚未入职，业务信息未知，必须可零代码扩展 |
| 度量先行 | M1（海外引擎）先于 M2（公司档案 Schema） | 不先装仪表盘，后续改动无法判断是否有效 |

### 5.1 本次二次开发的两个核心缺口

这两点是「部署 + 录数据」之外**真正需要写代码**的地方：

1. **AI 可见性只支持国内引擎** —— 采样提供商只有 `doubao_ark_responses` / `doubao_search_custom` / `deepseek_analysis`，而目标市场在欧美。**不接入海外引擎就没有验收标准。**
2. **Organization Schema 只有一个 `name` 字段** —— 需求明确要求「提供**结构化**设计资质与合规标准」，但当前生成的 JSON-LD 缺 `sameAs` / `award` / `brand` / `hasCredential`。**`sameAs` 缺失尤其关键**：AI 靠它把 LinkedIn、B2B 店铺、官网归并为同一实体。

> 缺口 2 属于 **M2 里程碑**，**不在当前计划范围**，需要另写一个实现计划。

`ljccc2025/GEO` **目前是公开仓库**，里面有公司的 GEO 获客策略、目标市场、品类等信息。后续还会加入更多业务细节（能力点、客户画像、目标问题清单）。

**需求方明确选择了保持公开**，但你应该知道这个风险，并建议他们重新评估。

### 9.2 虚拟机密码是 `1`

极度弱口令。**建议立刻修改**：

```bash
passwd root
```

### 9.3 🔴 有一个真实 API Key 已泄露

需求方桌面的 `E:\学习\排错.docx`（一份 k8s 排错笔记）里含**真实密钥**：

- 一个真实的 `DEEPSEEK_API_KEY`（`sk-` 开头）
- 一个 `JWT_SECRET`
- MySQL root 密码

**本次工作没有把这些写进任何文件**，但要提醒需求方：

1. **去 DeepSeek 后台吊销那个 key 并重新签发**
2. 检查该文档是否通过截图、网盘等渠道流出过

### 9.4 密钥纪律

- API Key 一律通过**后台配置界面**写入（GEOFlow 加密存储），**不得**提交到代码库
- 本仓库是公开仓库，**任何写进文件的密钥都视为已泄露**
- `.env` 与 `.env.prod` 不要提交

### 9.5 安全敏感代码改动

`AiProviderEndpointPolicy` 是**防 SSRF 的控制**。项目规则明示「**绝不允许绕过**」。
扩充白名单时必须：

- 不改 `isTrustedHttpsUrl()` 的校验逻辑（HTTPS 强制、拒绝 URL 内嵌凭据、拒绝主机名后缀伪装）
- 不放宽为通配或跳过校验
- 配套单元测试，**同时**断言「新端点放行」与「非白名单仍拒绝」
