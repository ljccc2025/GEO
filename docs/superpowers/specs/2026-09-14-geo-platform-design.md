## 1. 背景与目标

### 1.1 业务背景

公司是**工业设计出口企业**，当前品类为**耳塞**（后续可能扩展其他品类）。目标客户是**海外买手**。

公司目前**没有域名、没有官网**，也没有 GEO 相关系统。

### 1.2 要解决的问题

海外买家的采购习惯正在从「搜索引擎 → 逐个点开网页」转向「直接问 AI」。
当买手问 AI「推荐中国优秀的耳塞设计工厂」时，AI 给出的答案里**没有我们公司**——因为 AI 不知道我们存在。

### 1.3 目标

让 AI 在回答设计 / 供应商相关问题时，**答案中包含并推荐我们公司**。

### 1.4 打法（已确认）

**真实内容 × 广泛分发。**

不做内容农场。AI 引擎和搜索引擎都在识别低质 AI 生成内容，编造内容 × 批量投放会被过滤，严重时域名被打标记。
系统的内容质量门禁是这套打法能否长期有效的关键。

### 1.5 成功定义

建立可度量的 AI 可见性闭环：能量化「目标问题上 AI 是否提及我们」，并让这个指标随内容建设而改善（见 §8.2）。

## 2. 范围

### 2.1 子项目划分

原始需求包含三个互不重叠的能力，拆为三个子项目，**本规格只覆盖子项目 1**：

| # | 子项目 | 说明 | 状态 |
|---|---|---|---|
| **1** | **GEO 作战平台** | 内容生产 + 质检 + 分发 + AI 可见性度量 | **本规格** |
| 2 | 多模态以图搜图 | 买手上传样品图 → 匹配内部款式库与打样方案 | 待后续 |
| 3 | 企业微信引流 | 独立站访客 → 企微客户群 | 待后续 |

**顺序依据**：子项目 2 和 3 是**流量转化与沉淀工具**。没有子项目 1 产出的流量，做出来也是无源之水。先造内容产能，再开店。

### 2.2 本子项目的范围内

- GEOFlow 的部署与配置
- 二次开发（见 §5）
- 内容生产链路打通（知识库 → 生产 → 质检 → 分发）
- AI 可见性度量能力（针对海外引擎）
- 公司结构化档案与 Schema 输出

### 2.3 本子项目的范围外

| 不做的事 | 原因 |
|---|---|
| 面向买手的公司官网 | 本子项目交付的是**内部作战平台**，不是展示站 |
| 多租户 / 对外提供 GEO 服务 | 已确认**对内单租户** |
| 以图搜图 | 归子项目 2 |
| 企业微信集成 | 归子项目 3 |
| 自动化的可见性阈值告警 | YAGNI：阈值需要先积累数据才能定，先做人工触发 |
| 产品图库 / 3D 展示 / 在线交易 | 与 GEO 目标无关 |

## 4. 架构决策

### 4.1 决策：以 GEOFlow 为底座，一体化部署

**GEOFlow**（`yaojingang/GEOFlow`，3.6k star，PHP 8.3 / Laravel，AGPL-3.0）作为唯一底座。

理由：

1. **它是一个 Web 应用**——管理后台 + 内容生产 + 质检 + 分发 + 可见性分析，正是本项目要交付的「作战平台」形态
2. **能力闭环最全**——候选项目（GEORank / elmo / getcito）都只做诊断或监测，不含内容生产流水线
3. **企业级治理现成**——权限体系、审计留痕、签名更新 + 完整备份 + 恢复点回滚、出站请求管控与防 SSRF
4. **配置驱动**——知识库、关键词库、标题库都是后台可管理的表，契合 P6（业务信息未定，必须可配置）
5. **支持简体中文界面**（`lang/zh_CN/`）

### 4.2 被否的方案

| 方案 | 否决理由 |
|---|---|
| **GEOFlow 内容工厂 + 独立官网** | 原以为官网要承载产品展示，但已确认**不需要官网**，拆分的核心理由消失 |
| **GEORank + 自研内容生产** | 许可证最干净（Apache-2.0），但**不含建站、不含内容生产**，工作量最大 |
| **纯自研** | 放弃 GEOFlow 已积累的 408 次提交与 323 个测试文件，不经济 |

### 4.3 许可证边界（AGPL-3.0）

GEOFlow 是 AGPL-3.0。本项目的用法：

| 做法 | 判断 |
|---|---|
| 内网部署给公司同事使用 | 安全。用户即员工，内网放源码仓库即满足义务 |
| 它生产的**文章内容**发布到公开网络 | 安全。内容不是软件的衍生作品，著作权归公司 |
| 部署含 GEOFlow front controller 的动态站点给公众访问 | 触发源码提供义务 |
| 修改 GEOFlow 核心 PHP 后公开部署 | 必须开源修改 |

**约束**：本子项目**不对公众暴露任何 GEOFlow 运行实例**。分发出的站点若面向公众，只使用**静态产物**。

### 4.4 部署形态

Docker Compose，公司服务器，内网访问。

| 类别 | 容器 |
|---|---|
| 基础 | `postgres`(pgvector) · `redis` · `init` · `app` · `web` |
| 队列 worker | `queue` · `ai-quality-queue` · `ai-quality-backfill-queue` · `ai-optimization-queue` · `knowledge-queue` |
| 其他 | `scheduler` · `reverb` · `default` |

运行要求：PHP 8.3+ / PostgreSQL（pgvector）/ Redis / Node.js（前端资源构建）/ Nginx + php-fpm。

## 5. 二次开发范围

### 5.1 开发项 1（M1）：海外引擎接入

**问题**：GEOFlow 的 AI 可见性采样目前只有三个提供商，**全部是国内引擎**：

```php
// app/Models/AiVisibilityRun.php  L21-29
const PROVIDER_DOUBAO_ARK_RESPONSES = 'doubao_ark_responses';
const PROVIDER_DOUBAO_SEARCH_CUSTOM = 'doubao_search_custom';
const PROVIDER_DEEPSEEK_ANALYSIS    = 'deepseek_analysis';
const SAMPLE_PROVIDERS = [DEEPSEEK_ANALYSIS, DOUBAO_ARK_RESPONSES, DOUBAO_SEARCH_CUSTOM];
```

目标市场在海外，测国内引擎等于**没有验收标准**。

**已核实的扩展点**：模块结构清晰，每个提供商一个独立 Client 类（`DoubaoArkResponsesClient` / `DoubaoSearchCustomClient` / `DeepSeekAnalysisClient`），`AiVisibilityService` 每个提供商一个 `run*` 方法。

**要求**：

| # | 要求 |
|---|---|
| R1.1 | 新增**两个**海外引擎采样提供商：**Perplexity**（真实网页检索型）与 **OpenAI**（ChatGPT Search 系） |
| R1.2 | 新增的提供商必须挂进 `AiVisibilityRun::SAMPLE_PROVIDERS`，使既有分析代码自动生效 |
| R1.3 | 每个新提供商实现为独立 Client 类，遵循既有 Client 的结构与错误处理约定 |
| R1.4 | 支持在后台配置各引擎的 API 凭据与模型绑定 |
| R1.5 | 采样结果写入 `ai_visibility_runs`，字段与既有提供商一致（含回答原文） |
| R1.6 | 分析用提示词须支持**英文**，不得硬编码中文提示词 |
| R1.7 | 扩展 `AiProviderEndpointPolicy` 的 HTTPS 域名白名单以放行新增端点 |
| R1.8 | R1.7 的改动**不得绕过或削弱**既有 SSRF 防护；遵循项目既有安全验证流程 |
| R1.9 | 复用 `AiSourceProvider` 既有的 `daily_limit` / `used_today` 配额机制做成本控制 |

**自动受益**：8 个引用 `SAMPLE_PROVIDERS` 常量的文件（分析、竞品检测、报表等）无需改动。

### 5.2 开发项 2（M2）：公司档案 + 结构化 Schema

**问题**：需求明确要求「提供**结构化**设计资质与合规标准，方便 AI 抓取」。但当前生成的 Organization schema 只有一个名字：

```php
// app/Services/GeoFlow/DistributionTargetSitePackageBuilder.php  约 L3322
"publisher" => [ "@type" => "Organization", "name" => $settings['site_name'] ],
```

**要求**：

| # | 要求 |
|---|---|
| R2.1 | 新增「公司档案」实体，承载**结构化**的公司事实（非自由文本） |
| R2.2 | 档案字段至少覆盖：`sameAs`、`award`、`brand` / `memberOf`、`hasCredential`、`knowsAbout`、`address`、`contactPoint`、`logo`、`url`、`description` |
| R2.3 | 提供后台界面录入与维护公司档案 |
| R2.4 | 新增独立服务，把公司档案渲染为 Organization JSON-LD |
| R2.5 | 站点生成时注入完整的 Organization JSON-LD，替换现有只有 `name` 的实现 |
| R2.6 | 生成的 JSON-LD 通过 Schema.org 结构校验 |

**`sameAs` 是本开发项最关键字段**：它告诉 AI「LinkedIn 主页、B2B 平台店铺、官网页面是同一家实体」。缺失它，AI 无法把散落各处关于本公司的信息归并为一个实体，也就无法累积成「值得推荐的供应商」。

**约束**：`DistributionTargetSitePackageBuilder.php` 有 **3796 行**，属巨型文件。本开发项**只做定点替换**（把 Organization JSON-LD 段改为调用新服务），**不重构该文件**（不做无关重构）。

### 5.3 开发项 3（M3）：品牌化

配置为主：站点名称、logo、配色、界面语言（简体中文已支持）。开发量预计很小。

### 5.4 开发项 4（M3）：业务模板

配置为主：工业设计 / 耳塞品类的知识库结构、选题模板、质检规则。以**后台录入**为主，少量规则调优。

### 5.5 明确不做

- 不新增「业务配置中心」——现有载体足够（见 §6）
- 不重构 `DistributionTargetSitePackageBuilder.php`
- 不实现自动阈值告警
- 不改动 GEOFlow 的分发、质检、权限、审计等既有子系统

## 6. 业务配置层

### 6.1 设计约束

前提 P6：业务信息（品类、能力点、目标问题、客户画像）**目前未知**，入职后补齐。因此系统必须把这些做成**数据**而非代码。

### 6.2 载体映射

| 业务概念 | GEOFlow 载体 | 需开发 |
|---|---|---|
| 品类 / 业务线 | `knowledge_bases.business_line` + 关键词库分组 | 否 |
| 能力点 / 核心竞争力 | 企业知识（`enterprise_knowledge_*`） | 否 |
| 资质与合规标准 | 知识库（含 `source_url` / `source_type` / `risk_level` / `effective_date`） | 否 |
| 目标问题（完整问句） | 关键词库（`keyword_libraries` / `keywords`） | 否 |
| 设计获奖记录 | 知识库 **+ 需结构化输出** | **是（R2.2）** |
| 合作品牌名单 | 知识库 **+ 需结构化输出** | **是（R2.2）** |
| 案例与素材 | 图片库 / 素材库 / 文章 | 否 |

**结论**：载体够用。只有「获奖」和「合作品牌」因为需要**结构化输出**而需要开发。

### 6.3 已知限制

| # | 限制 | 处理 |
|---|---|---|
| L1 | 目标问题长度限制 **100 字符**（`mb_strlen($keyword) <= 100`） | 记录为约束。一般问句够用；超长多条件问句拆成多条。**暂不修改**，待实际使用后评估 |
| L2 | 后台采集单次最多选 **50 个**目标问题 | 分批采集 |

## 7. 数据流

```
1 录入    运营同事在后台录入：知识库 / 企业知识 / 关键词库 / 公司档案(新)
             |
2 生产    知识切片 -> 向量化(pgvector) -> 任务选题 -> AI 写作 -> AI 质检门禁 -> 人工审核
             |
3 分发    已发布文章 -> 托管站点 / 目标站点包 / WordPress REST / 通用 HTTP API
          （每个站点自带 Schema + sitemap + llms.txt；注入完整 Organization 档案）
             |
4 度量    目标问题 -> 采集海外引擎真实回答 -> 分析可见率/排名/情感/信源偏好 -> 竞品检测
             |
5 反馈    可见率下降 -> 定位相关文章 -> 人工生成优化任务 -> 回到 2
```

### 7.1 存储落点

| 阶段 | 主要表 |
|---|---|
| 1 | `knowledge_bases` · `enterprise_knowledge_*` · `keywords` · **`organization_profiles`（新增）** |
| 2 | `articles` · `article_ai_quality_checks` · `article_reviews` |
| 3 | `distribution_channels` · `article_distributions` · `distribution_logs` |
| 4 | `ai_visibility_runs` · `ai_visibility_sources` · `ai_visibility_competitors` |

### 7.2 开发项与链路的关系

- **开发项 2（公司档案）** 横跨 1 → 3
- **开发项 1（海外引擎）** 只动 4，不碰 1 / 2 / 3

两个开发项**在链路上互不重叠**，可独立开发与验收。这是 M1 / M2 划分的依据。

### 7.3 反馈闭环的自动化程度

**第 5 阶段为人工触发**。看到可见率下降后，人工定位相关文章并生成优化任务。

原因（YAGNI）：自动阈值需要先积累数据才能确定阈值取值，当前基线未知，任何阈值都是猜测。待数据充分后再评估自动化。

## 8. 测试策略

### 8.1 代码级

项目现有 **323 个测试文件**（Feature 176 + Unit 103）+ CI（`.github/workflows/ci.yml`）。新代码必须配套测试，遵循既有惯例（PHPUnit、`tests/Feature` 与 `tests/Unit`）。

| 被测对象 | 测试类型 | 要求 |
|---|---|---|
| 新增的海外引擎 Client | Unit | mock HTTP，**不打真实 API** |
| Organization JSON-LD 渲染服务 | Unit | 给定档案，断言输出结构与字段 |
| 可见性采集链路 | Feature | 覆盖成功与失败路径 |
| 端点白名单策略改动 | Unit | 断言允许新增端点、仍拒绝非白名单端点 |

### 8.2 业务验收标准

| # | 验收项 | 阶段 |
|---|---|---|
| **AC1** | 能用海外引擎跑通一次完整采样，结果入库并在看板显示 | M1 |
| **AC2** | **基线落库**：记录项目起点时「AI 是否提及本公司」的状态 | M1 |
| **AC3** | 分发站点的 Organization JSON-LD 通过 Schema 校验，且含 `sameAs` / `award` / `brand` | M2 |
| **AC4** | 目标问题的**可见率相对基线产生可观测变化**，按周采样观察趋势 | M2 后 |

**AC4 不设固定数值阈值**：基线尚未测量，任何阈值都是无依据的猜测。先建立趋势曲线，待数据充分后再设定目标值。

### 8.3 采样随机性

同一个问题多次询问 AI，回答可能不同。因此：

- 单次采样**不构成结论**
- 验收必须建立在**多次采样的趋势**上
- GEOFlow 看板已提供「采样质量」指标，应在验收中一并查看

## 9. 里程碑

| # | 里程碑 | 内容 | 产出 |
|---|---|---|---|
| **M1** | 海外引擎接入 | 开发项 1 + 测试 | 度量能力 + 项目基线 |
| **M2** | 公司档案 + 结构化 Schema | 开发项 2 + 测试 | 结构化产出能力 |
| **M3** | 品牌化 + 业务模板 | 开发项 3、4 | 可投入日常运营 |

**顺序依据**：不先建立度量能力，后续所有改动都无法判断是否有效。M1 同时产出项目基线，这是后续一切对比的起点。

**实现计划的范围**：M3（品牌化、业务模板）本质是**后台配置与内容录入**，不是编码工作，因此**不进入实现计划**。实现计划覆盖 M1 与 M2，按 M1 优先分阶段编排。

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| **R-1** | 公司服务器无法访问海外 API（A1 未验证） | M1 无法落地 | M1 第一步验证；不成立则先解决网络条件 |

| **R-6** | 业务信息（P6）入职后可能与设计假设冲突 | 需调整配置层 | 已通过配置化设计化解；冲突时只改数据不改代码 |

## 11. 术语表

| 术语 | 含义 |
|---|---|
| **GEO** | Generative Engine Optimization，生成式引擎优化。让 AI 在回答问题时提及并推荐你 |
| **AI 可见性** | 在目标问题上，AI 回答中是否出现本品牌、是否引用本站为信源 |
| **llms.txt** | 放在网站根目录的说明文件，告诉 AI 这个站点有什么内容 |
| **Schema / JSON-LD** | 网页里嵌的结构化数据，让 AI 准确理解页面讲的是什么，而不是靠猜 |
| **sameAs** | Schema 字段，声明「这几个外部页面是同一家实体」，AI 靠它做实体归并 |
| **目标问题** | 希望 AI 在回答时推荐本公司的那些问题 |
| **质检门禁** | 文章发布前按知识证据、引文、广告规则、法规依据逐项检查，不通过则留在草稿 |
| **采样质量** | 同一问题多次询问 AI 的结果一致性度量 |
